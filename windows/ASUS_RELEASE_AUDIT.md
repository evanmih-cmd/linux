# ASUS Windows 11 Pro — continuation release audit

**Decision: NO-GO — 2026-10-09.** This audit does not authorize any destructive operation on the ASUS.

## Scope

- Owner creates the bootable Windows USB; USB creation is outside this issue and is not a blocker.
- RAIDXpert2 is the accepted allocation architecture. Proof of the ASUS controller/virtual-disk implementation is a separate physical-storage experiment.
- This issue must prove supported manual RAID target choice after SSD1 Offline, correct ESP → MSR → Windows → WinRE layout, successful production postinstall, and evidence-based acceptance.
- The single canonical password-free Autounattend.xml omits DiskConfiguration, DiskID, WillWipeDisk, AutoLogon and LogonCount; the same bytes are used by VM and ASUS. Stock Setup's empty-space selection failed in three previous attempts. The subsequently accepted *manual WinPE* DiskPart/DISM/BCDBoot/REAgentC route reached a first Windows desktop on the existing two-disk VM. Repeated logon and runtime acceptance are still unproven; do not treat this as a complete unattended-Setup GUI workflow. Production release remains NO-GO.

## Two-disk Setup failure (2026-10-08) — actual live evidence

- Separate VM Desktop-Windows-11-Pro-TwoDisk booted from verified official
  Windows ISO, same common answer XML.
- Real operator selected target 96 GiB Unallocated Space while protecting
  original Home-like 8 GiB synthetic disk.
- **Windows Setup FAILED** (generic error dialog). Read-only NTFS extraction
  of target VDI recovered actual Panther setupact.log + setuperr.log.
- Fatal error in Finalize: BFSVC ServicingBootFiles failed 0x1F; Update Boot
  Code failed 0x8007001F (17:22:50 guest Setup log timestamp).
- Raw GPT on intended target: ONLY MSR and NTFS OS partition, NO ESP.
- Source protected VDI: raw GPT + MBR and protected data-sentinel checksum
  all match original manifest. Sentinel integrity PASS is not boot proof.
- **Invalidated assumption:** stock Setup cannot be presumed to create an
  independent ESP simply because an existing other disk was set Offline.
- Therefore the prior "Offline + Setup UI Unallocated Space + Next" procedure
  is UNSAFE/INSUFFICIENT for the independent two-Windows design.
- Microsoft documents deterministic UEFI/GPT partitions via WinPE DiskPart
  and target-bound BCDBoot /s; UEFI NVRAM entry is NOT generated by /s.
  **Required choice is physical boot disk/RAID LUN in the firmware boot
  menu**, not selection between Windows Boot Manager entries.
  ASUS firmware support for boot-device selection of the RAIDXpert2 LUN
  must be proven on the physical laptop.
  Replacement manual Microsoft deployment was subsequently executed and
  reached the Windows 11 desktop once. Full runtime/dual-boot acceptance is
  NOT PROVEN. Absolutely NO ASUS installation release.
- Source logs (outside repository):
  ~/.cache/desktop-windows-two-disk/diagnostics/
- Canonical installed VM unaffected. Failed VM left on diagnostic screen.

## Persistent firmware disk priority experiment (2026-10-08)

The VirtualBox two-disk UEFI firmware had existing Boot0004 (protected SATA0)
and Boot0005 (target SATA1) entries when inspected via mutable SOAP session.
The registered-machine handle's incomplete list previously caused a false
conclusion that BootOrder was absent. VirtualBox's BIOS-only type-level
setting is irrelevant; IUefiVariableStore_changeVariable successfully
changed permanent BootOrder from 0004-before-0005 to 0005-before-0004
with ISO entries still ahead, all other entries intact. Readback PASS,
Secure Boot true, SATA ports unchanged. The same existing VM rebooted
into stock Setup with unchanged XML. The GUI still enumerates protected
Disk 0 and target Disk 1. ESP creation and Windows setup success for this
permanent-firmware-order experiment are STILL PENDING manual target choice.

## Verified facts

- 2026-10-09: The same two-disk VM reached an actual Windows 11 desktop once after operator-controlled WinPE DiskPart/DISM/BCDBoot/REAgentC and the canonical XML. A subsequent SOAP check found Running but a black framebuffer, with Guest Additions/Guest Control unavailable. Shift and a non-destructive ACPI shutdown request did not resolve it; no hard reset or reinstall was performed.
- 2026-10-09: Attached answer ISO at SATA port 4 was extracted independently: its 3379-byte XML matches `windows/vm/deployment/Autounattend.xml` byte-for-byte (SHA-256 `8ef765a139dbbcc811f90b3df6f191c8f0405c154c350ddbc6d4672e50e4d5e4`) and has no Password, AutoLogon or DiskConfiguration elements. A stale 3572-byte cached historical XML containing a Password element was discovered outside the repository; it was **not** attached to the VM. The existing `build_answer_media()` generator replaced that cache with the canonical password-free XML/ISO. No VM media was detached or changed.
- 2026-10-09: Read-only host audit of the *current*, BitLocker-marked (`-FVE-FS-`) VDI: **17 PASS, 0 FAIL, 6 NOT_PROVABLE_ENCRYPTED**. Protected GPT/sentinel, target local ESP/BCD, WinRE image and GPT geometry passed. Because the VM was Running, regard the readback as provisional pending powered-off parity and Windows-side runtime evidence.
- 2026-10-09: Installer/harness unit tests **73 PASS**, static preflight and canonical XML contract **PASS**. These do not override the runtime or hardware NO-GO gates.
- Official Microsoft source ISO: SHA-256 matched the stored provenance.
- Latest available elevated audit of the **original one-disk VM**, not this new two-disk installation: **24 PASS / 5 FAIL / 8 NOT_PROVABLE_IN_VM**.
- VM FAIL: BitLocker FVE TPM/PIN policy not applied, Sandbox optional feature disabled, BitLocker Protection Off with zero protectors (two failed checks), Administrator Protection mode still 1.
- VBS/HVCI policy present, but NEM guest cannot prove running VTL1, physical ESS/Pluton/Secure Launch or real hardware recovery.
- The common workstation DSC no longer writes DeviceGuard/HVCI Locked=0; hardware-only security-hardware.winget exclusively writes Locked=1 after physical acceptance.
- New manual-target XML structural contract PASSES while release_status=BLOCKED and safe_for_asus_install=false.
- Production release staging fails closed **before writing** unproven installation media; regression tests protect the no-auto-target invariant.

## Reproduction and boundaries

- Run from windows/vm/harness: `python3 -m unittest -q`, `python3 bench.py contract`, `python3 bench.py audit`, `python3 release_readiness.py PATH_TO_LIVE_ELEVATED_AUDIT.json`.
- Running the legacy contract is **not** a substitute for testing the final owner-selected target/RAID layout. Read-only VM facts alone do not imply hardware acceptance.
- This version audits safety and desired state. A two-disk VM manual deployment and first boot occurred on 2026-10-09. It has not completed repeated login/runtime Windows security or WinRE acceptance, real LUN expansion, WinRE recreation, production key enrollment, firmware-lock enrollment, or physical ASUS provisioning.
