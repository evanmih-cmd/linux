# Приёмка ручного развёртывания Windows 11 Pro из штатной WinPE

**Основной одобренный аудитор — два обычных текстовых файла: [AUDIT.CMD](AUDIT.CMD) и [EXTRA.JS](EXTRA.JS).** Никаких собственных EXE, PowerShell, Python или модификаций образа WinPE. Эти два файла можно прочитать и проверить перед запуском.

В `AUDIT.CMD` используются только штатные `cmd.exe`, `diskpart`, `fsutil`, `find`, `bcdedit`, `reagentc` и `cscript.exe`. Дополнение `EXTRA.JS` использует встроенные компоненты Windows Script Host: FileSystemObject, MSXML6 и WMI (`Win32_DiskDrive`, `Win32_DiskPartition`, `Win32_LogicalDiskToPartition`). Доступность всех компонентов **проверена непосредственно на официальном установочном WinPE стенда**.

## Запуск

Поместить **оба файла рядом** на установочную флешку или отдельный читаемый носитель. В WinPE открыть `Shift+F10`, определить номера дисков и буквы разделов вручную командой `diskpart` → `list disk` / `detail disk` / `list volume`. Убедиться, что защищённый SSD1 находится Offline. Из DiskPart выйти.

На текущем VirtualBox-стенде: защищённый диск `0` (8 ГиБ), целевой `1` (96 ГиБ), ESP `S:`, Windows `W:`, WinRE `R:`, канонический `Autounattend.xml` на `G:`, скрипты на `I:`:

```cmd
I:\AUDIT.CMD 1 0 S W R G
```

На ASUS **НЕ переносить номера дисков**: они обязаны определяться заново по реальным моделям/размерам:

```cmd
U:\AUDIT.CMD N M S W R F
```

Здесь `N` — фактически подтверждённый номер целевой RAID LUN, `M` — фактически подтверждённый номер защищённого SSD1 (он должен быть **Offline**), `U:` — буква флэшки с `AUDIT.CMD` и `EXTRA.JS`; последний аргумент `F` — **буква носителя с исходным `Autounattend.xml`**, без двоеточия. Если XML находится на той же флэшке, что и скрипты, шестым аргументом будет `U`. Буквы `S`, `W`, `R` — назначенные ранее целевые ESP, Windows и WinRE (также без двоеточий). Ни `N`, ни `M`, ни `F` не являются буквальными аргументами: подставить реальные номера и буквы. В обоих вариантах номера дисков и буквы передаются только оператором.

**Точка запуска в общем порядке:** после завершения `DISM /Apply-Image`, интеграции AMD RAID (если требуется), `bcdboot`, создания и регистрации WinRE и копирования канонического XML в `W:\Windows\Panther\Unattend.xml`, **до первой перезагрузки**. Убедиться, что файлы реально существуют (`dir U:\AUDIT.CMD`, `dir U:\EXTRA.JS`, `dir U:\Autounattend.xml` при одном и том же USB `U:`). После запуска скрипт печатает `SUMMARY PASS=... FAIL=... NOT_PROVABLE=...`. При `FAIL>0` установка не принята, и перезагружаться до диагностики не следует. Отдельная точная инструкция — в [главном runbook, раздел «Обязательный запуск WinPE-аудита»](../deployment/README.md#обязательный-запуск-winpe-аудита-auditcmd).

При необходимости отчёт записывается на **флешку, не на SSD**:

```cmd
U:\AUDIT.CMD N M S W R F > U:\audit-report.txt
```

## Что проверяется

- Read-only DiskPart: защищённый диск Offline, целевой GPT с четырьмя разделами, типы ESP, MSR и Recovery, правильные атрибуты Recovery.
- WMI сопоставляет `S:/W:/R:` именно с **целевым физическим диском**, проверяет точные смещения в байтах: ESP 300 МиБ, пропуск MSR 16 МиБ, Windows на остальном пространстве и WinRE **2048 МиБ в конце**.
- Наличие и корректность целевого ESP FAT32, Microsoft EFI/BCD, Windows NTFS, файлов ОС и WinRE. BCD проверяется **штатным BCDEdit**.
- ReAgentC и XML регистрации WinRE: GUID целевого GPT-диска и **точное смещение** Recovery должны совпасть с данными WMI/DiskPart.
- `Panther\Unattend.xml` проверяется на наличие `specialize` и `oobeSystem` и отсутствие `DiskConfiguration`, а `cscript` проверяет **побайтовое равенство** с каноническим `Autounattend.xml`. Для побайтового сравнения ASCII XML FileSystemObject читает по одному ASCII-символу на исходный байт, сверяет длину файла и каждого прочитанного символа (ASCII 0–127), а затем сравнивает все байты. Это работает и при **нечётной длине**. Не-ASCII файл без надёжного бинарного считывателя даёт FAIL, а не ложный PASS. Недопустимый формат сравнения — FAIL, а не ложный PASS.

**Безопасность:** `diskpart /s` внутри аудита использует только `list`, `select`, `detail`, `uniqueid disk` (без `id=`). Ни одной команды `clean`, `format`, `create`, `shrink`, `remove`, `assign`, `online` или изменяющей BCD/реестр. Временные отчёты записываются исключительно на RAM-диск `X:`. `EXTRA.JS` вообще не создаёт файлов и не запускает процессов. Это **аудит**, а не скрипт установки.

**Для физического AMD RAID:** этот read-only GPT/BCD/WinRE-аудит **не доказывает**, что `rcbottom`/`rcraid` стали boot-critical в offline установленной Windows или что WinRE видит RAID LUN. Дополнительные DISM-проверки `Boot Critical`, фактическая загрузка WinOps и доступ из WinRE обязательны по [AMD_RAID_BOOT.md](../deployment/AMD_RAID_BOOT.md). `PASS` этого аудитора нельзя использовать вместо них.

**Диагностика геометрии при `FAIL`:** актуальный `EXTRA.JS` в draft-ветке теперь сообщает конкретное нарушенное сравнение **в байтах** (`esp_size_bytes`, `winre_size_bytes`, `msr_gap_bytes`, `windows_winre_gap_bytes`, `disk_tail_bytes`, `windows_size_bytes`) вместо безымянного `Wrong_partition_sizes_offsets_or_tail`. Строгие условия принятия не ослаблены. **На физической ASUS USB может находиться прежняя копия** `EXTRA.JS`, которая ещё печатает только общий FAIL; новая версия в GitHub не обновляет флэшку автоматически. Для уже работающей WinPE сначала прочитать существующий `X:\Windows\Temp\winpe-accept\diskpart.txt` без изменения состояния дисков.

## Границы доказательств

`FAIL` означает обнаруженное нарушение. `NOT_PROVABLE` остаётся только там, где недостаточно данных или проверка невозможна **до загрузки новой ОС**, а не из-за отсутствующего `findstr`/PowerShell/средства сравнения XML:

- загрузка именно с целевого диска, Secure Boot в работающей Windows, редакция Windows Pro и состояние WinRE Enabled — проверяются после первого запуска;
- полная побайтовая неизменность SSD1 требует **заранее снятого эталона**;
- raw CRC заголовков и резервной таблицы GPT не выдаются штатными DiskPart/WMI; на стенде отдельно проверяются сохранённым Linux/VDI-аудитом. На ASUS для этой *дополнительной* проверки нужен иной обоснованный read-only источник сырых секторов; отсутствие такой проверки не следует маскировать PASS.

**Фактический live-run в установочной WinPE стенда, 2026-10-09:** `29 PASS / 0 FAIL / 6 NOT_PROVABLE` после исправления CRLF. Независимые существующие Linux/VDI-проверки: `23 PASS / 0 FAIL`. Самостоятельная загрузка Windows 11 Pro пока не проверена, общую установку нельзя объявлять PASS.

Сохранённый Python-VDI harness **не изменён и не заменён**. Предыдущее собственное приложение `winpe-audit.exe` не входит в одобренный WinPE-путь и **не должно копироваться на ASUS**.
